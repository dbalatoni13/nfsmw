## 2. `QuickRaceUnlocker::IsCarUnlocked` (1.496 B) — CERRADA al 100 %

**El mecanismo, y es reutilizable: el número de expansiones inline del
DESTRUCTOR en el DWARF es el número de `return` que tenía el original.**

`dwbody.py` sobre la función:

| | `frontend::~frontend()` | `GetCareerSettings` | `GetCurrentBin` |
|---|---|---|---|
| ORIGINAL | **21** | 19 | 15 |
| NUESTRO | **41** | 19 | 15 |

`CarAttribs` es un `Attrib::Gen::frontend` con destructor, así que **cada `return`
del ámbito expande el destructor**. Nuestro fuente tenía exactamente 41 `return`
(contados: 19 parejas `if(...) return false; return true;` + `default: return
false;` + dos `return answer;`). El original, 21.

La estructura que da 21 y **el mismo código emitido**:

```cpp
    if (fe_car->MatchesFilter(0xF0007)) {
        switch (fe_car->GetType()) { ... answer = true; ... }
    } else if (fe_car->MatchesFilter(0xF0008)) {     // <- `else if`: sobraba un `return answer;`
        switch (fe_car->Handle) {
            case 0x965F:
                if (FEDatabase->GetCareerSettings()->GetCurrentBin() >= 2) {
                    break;                            // <- era `return false;`
                }
                return true;
            ...
            default:
                break;                                // <- era `return false;`
        }
        return false;                                 // <- uno solo para las 20 salidas
    }
    return answer;
```

19 `return true` + 1 `return false` + 1 `return answer` = **21**. El `jump.c`
funde las colas y salen los **tres** bloques de salida del objetivo
(`~Instance` + `li r3,1` / `li r3,0` / `mr r3,r30`), idénticos a antes.

### Por qué mueve los registros

`lreg.py` da la causa exacta. Los dos pseudos intercambiados eran:

    pseudo n_refs live_len prioridad reg
    1398   44     722      3047      r31   <- copia de &CarAttribs (la crea regmove)
    102     6      48      2500      r28   <- fe_car

El objetivo quiere `fe_car` en r31 y la copia en r28, o sea prio(102) >
prio(1398). Los 44 refs de 1398 **son los sitios del destructor**: 41 `return` +
la copia + los dos usos. Bajarlos a ~24 hunde `floor_log2(44)=5` a
`floor_log2(24)=4` y la prioridad de 3047 a ~1300; `fe_car` pasa delante y se
lleva r31. **12 diffs → 0.**

|---|---|---|
| base | 41 `return` | 99,83957 % · 12 diffs |
| **c1** | **21 `return` (arriba)** | **100,00000 % · 0 diffs** ✔ |

## 8. HERRAMIENTA: `dwbody.py` puede estar leyendo un volcado RANCIO

**Lo más importante para el siguiente.** El lado «nuestro» de `dwbody.py` sale de
`build/regmap/our_<unidad>_<tam>_<mtime>.nothpp`, y **sólo se regenera cuando
alguien llama a `regmap.py <unidad> <func> --ours`**. `dwbody.py` no lo
regenera, y `regmap.py <unidad> --list` **tampoco**.

Medido hoy: el `.nothpp` de zWorld2 era del **4-sep 14:45** con
`WRoadNetwork.cpp` tocado el **5-sep 18:42**; el de zPhysics del 4-sep con
`Smackable.cpp` del 5-sep. Con la caché rancia, `CookieTrailCurvature` enseñaba
una local `selected_width` **que no existe en el árbol** (venía de un ensayo de
otra ronda) y **escondía** el hallazgo real (`sina`, §3).

**Receta: antes de fiarte de un `dwbody`, ejecuta
`python scripts/regmap.py <unidad> "<Clase::Funcion>" --ours` y comprueba que
aparece un `.nothpp` con la fecha de hoy.**

(Las conclusiones de la r23 sobre las cuatro atascadas las he rehecho con caché
fresca y **se sostienen** — §7.)
